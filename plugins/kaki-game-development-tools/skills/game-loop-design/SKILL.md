# 游戏循环设计

## 职责

首要目标是让读者看懂游戏怎么玩：玩家反复做什么、依据什么信息选择、获得什么反馈、何时进入其他玩法或结束。用循环描述各个玩法及其衔接，并实际绘制可编辑的游戏循环图。节点粒度以表达清楚为准，无需完整复现系统执行、逐帧时序或程序调用。

## 必须遵守的绘图规则

- 只使用**行为、信息、分支、子循环**四类节点。行为是玩家操作；信息是玩家可获取的反馈、结果或事实；分支是选择或条件判断；子循环引用可单独展开的循环体。开始、结束、系统事件、状态或逻辑门不得另立节点类型；结果可用信息表达，必要成本或变化可用简短边标签表达。
- 每个循环体单独划定边界，在其内部设置“全局可获取信息”区域。逐项列出在该循环体内可显示或主动查询的信息；即使与其他循环体相同，也在各自区域明确标注。它们仍是信息节点，不串入步骤箭头；只在特定阶段出现的信息留在流程对应位置。
- 图中只保留循环名称、四类节点、全局信息区域和理解路径所需的简短连线标签。不要附加玩法介绍、策略建议、设计分析、实现说明、验证统计、免责声明或无关脚注；资料来源、假设及验证边界放图外。
- 保持行为和信息语义单一，但不为技术上的严格原子化增加阅读负担。按“主循环→子循环”逐层展开；图论、状态模型和量化分析只在用户需要时另行提供，不挤入玩法图。

体验与核心玩法取舍交给`game-design`；系统树和详细规则契约交给`game-system-design`；代码实现交给程序技能。不为了图形闭合擅自加入奖励、永久成长、商业化或留存机制。

现有游戏的资料采集、发行包分析与规则证据核查交给`game-analysis`；本技能据已知动作和规则绘图，保留推断／未知标记，不把拆解假设画成确认机制。

循环ID、行为引用和变更回交遵守[插件级路由与交接契约](../../references/skill-routing-and-handoff.md)；本技能拥有`LOOP-*`图与语义，不复制行为、配置或验收正文。

## 依据与读取

- 每次先读[循环设计与绘图约定](references/loop-contracts.md)。有既有规则时，以其版本、目标与行为ID为基线。
- 需要交付结构时读[循环设计模板](templates/game-loop-template.md)；首次绘图或核对例子时读[五步开箱循环示例](examples/five-step-loop.md)及其JSON。
- 需要讨论体验类别、层级与节律时，按主题读取同插件`../game-design/references/core-experience-design.md`的来源约定、相关主题的循环章节及第197页，并读对应勘误`../game-design/references/core-experience-design-errata.md`。不要求简单规则转图时重读全部200页。

## 工作流

1. 从用户输入或现有树提取玩家动作、可获取信息、选择／条件、反馈、返回点、退出及玩法之间的衔接。对每个循环体分别区分全局可获取信息和阶段性信息；未确认内容在图外标明。
2. 按实际时长选择小循环、单局／关卡循环及跨局循环；不强制凑三层。不把“打开菜单—关菜单”自动当核心玩法循环。
3. 为每个循环写一句可检验的闭环说明：入口→决策→行动→结果／反馈→变化→再次进入。没有成长的游戏写清策略学习／再次尝试，而非虚构跨局资源。
4. 只用四类节点建立有向边清单，标明每个节点所属循环体及全局信息作用域。分支注明条件，失败写明返回点或结束；自动结算用玩家收到的信息表达，不展开内部实现链。
5. 绘图：默认交付Markdown中的Mermaid源码；具备Python时可用随附脚本从明确布局的JSON生成SVG及Mermaid。两者来自同一节点／边表。用户指定Figma等环境时优先其可用工具与相应技能，不强制安装额外服务。
6. 从首次接触游戏的读者视角走读一条正常、一条失败／退出路径及一轮返回，检查能否看懂怎么玩、每个循环体的全局信息是否明确。保留会改变玩法选择的条件、费用和结果，省略不影响理解的执行细节。
7. 交付图与可编辑源；必要的循环说明、节点／边语义、来源及待验证假设放图外，按任务裁剪。检查实际渲染后才能称已预览；只有源码时明确未渲染，不把图形可达性当玩家体验验证。

## 绘图工具

`python scripts/render_loop.py examples/five-step-loop.json --output-dir <用户指定或项目输出目录>`

脚本只渲染明确节点、连线和坐标，不自动设计玩法、推断规则或优化布局。给出自定义图时按参考文档写JSON；输出为`loop.svg`、`loop.mmd`和`loop-check.json`。没有Python时直接写Mermaid与边表，注明渲染待完成；不因此阻断循环设计。

使用实际可用的Python 3解释器；Windows也可使用`py -3`，不要依赖指向应用商店的空启动别名。此脚本不需要PyYAML或图像转换库；它们如用于开发校验，应留在插件外。

## 质量门槛

- 读者能沿主线说出怎么玩、怎么选、收到什么反馈以及怎样进入下一轮；这是首要验收标准。
- 节点只有行为、信息、分支、子循环四类；每个循环体都有单独的全局可获取信息区域，信息的作用域和获取方式不凭空补造。
- 图内没有与循环体无关的描述；图外材料不强制全部展示。
- 所有循环都说明返回条件、每轮变化和再次进入的原因；非循环流程明确标为流程。
- 条件边可互斥覆盖，终止、拒绝与继续不能混成无标签箭头。失败回流不暗示免费重试，奖励回流不暗示保留本局数据。
- 原规则缺失时不能用一条“奖励→成长→挑战”套话冒充已知循环；区别建议与已确认机制。
- 图中稳定节点ID可映射到已有行为ID；原树变更后同步受影响节点和边，而非另画不一致的版本。
- 图形可读：标签可辨、箭头方向明确，回流路径尽量不穿节点。超过一屏可拆子循环并标入口／出口，不用巨图隐藏关系。
- 图表／脚本校验、规则数值模型、引擎运行和玩家体验测试分别报告。
