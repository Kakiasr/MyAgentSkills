# 游戏循环与绘图约定

## 语义先于画图

首要标准是读者能看懂游戏怎么玩。表达玩法主线、选择、反馈及玩法之间的衔接即可；不要求循环图严格重放所有系统执行。保持必要规则正确，不用逐帧时序、原子状态变量或图论分析挤占阅读空间。

循环的最小描述是：玩家带着什么目标进入，做何决策／行动，付出什么，得到什么反馈或结果，哪些条件改变了下次决策，为何再进入。不是每个节点都必须提供奖励，也不是每个游戏都有跨局成长。

- 小循环：一次短决策与反馈后再次决策；时间尺度按游戏事实填写。
- 单局／关卡循环：开始、反复决策、胜负或退出。
- 跨局循环：确有重试、解锁、积累或社交反馈时才画；“策略学习后重试”不等于角色永久成长。
- 系统执行流程：输入验证、扣费、事件、入账等可以是解释性子图，但应标为执行流程，不能代替玩家循环的目的和回返动机。

已有系统树时，节点引用行为ID，条件边引用规则ID。图可以简化实现细节，但不得颠倒胜负判断顺序，省掉费用，或把失败反馈画成成功奖励。

## 节点与连线

节点只使用以下四类，默认统一圆角框，通过颜色区分：

| 节点 | 含义 | 默认颜色 |
| --- | --- | --- |
| 行为 `action` | 玩家主动执行的一个清楚操作 | 浅蓝 `#edf2fc` |
| 信息 `information` | 玩家可获取的事实、反馈或结果；胜负结果也属信息 | 浅黄 `#fff2cb` |
| 分支 `branch` | 玩家选择或条件判断；出口标明选项／条件 | 浅红 `#ffe4e2` |
| 子循环 `subloop` | 引用可以单独展开的循环体 | 浅紫 `#eae1fc` |

循环体边界、信息区域和连线不是额外节点类型。没有独立子循环时无需凑满四类。开始用首个行为／信息表达，结束用结果信息或退出行为表达，不再使用独立开始、结束、状态、事件或逻辑门节点。系统结算一般折为玩家收到的反馈；需要技术分析时在图外另交付。

| 元素 | 填写内容 |
| --- | --- |
| 节点 | 稳定ID、玩家可理解的动作／决策／结果、已有规则引用、所在循环层 |
| 有向边 | 来源、目标、条件／结果、资源变化或说明；条件不明时标待决策 |
| 返回边 | 回到哪一步、是否消耗本次行动、保留／重置什么、再进入动机 |
| 终止位置 | 用信息节点表示胜负结果、行为节点表示退出；如能重试，另画选择和返回边，不暗示自动重开 |

不要将复杂AND／OR条件只写成“成功”。不同层级图之间用明确入口／出口或包含说明关联；兄弟子图不默认按从左到右执行。

## 每个循环体的全局可获取信息

每个循环体有独立边界和“全局可获取信息”区域，信息逐项用黄色信息节点表示，不串入步骤箭头。相同信息涉及多个循环体时，在各循环体分别标注。父循环区域不自动替代子循环区域；仅引用尚未展开的子循环时，在对应子图或交付清单补齐其信息作用域。

“全局”指在该循环体中不依赖某一步专门产生、可常驻显示或由玩家主动查询的信息，不表示整款游戏所有阶段通用，也不表示动画／遮罩期间每一帧都能查询。候选、奖励、单次结果等仅在特定阶段出现的信息放流程节点。内部变量不等于玩家可获取信息；获取入口不明确时在图外记录待核项。

例如在转轮构筑循环中，可核查当前金币、房租目标、剩余旋转次数、已持有符号／道具及可查询效果；不要照抄某个游戏的信息清单作为所有游戏的必填项。全局信息为空或尚未确认时也单独标明“无”或“待确认”，不得静默省略区域或编造可见性。

## 图内内容边界

图内只保留循环名称、四类节点、全局信息区域和理解路径必要的简短连线标签。不要添加开场介绍、策略提示、制作分析、技术说明、检查统计、免责声明或与循环体无关的脚注。来源、事实／假设、验证结果和不确定性按需写在图外，不为“图文齐全”强制扩展报告。

## 交付与验证

主图＋可编辑源＋必要图外说明足以完成小功能。较复杂游戏再拆层，不强制每次长篇策划案或边表。

交付前先从新读者视角确认能说出怎么玩，再走读一条正常路径、一条失败／退出路径、一次回返；检查每个分支出口。全局信息不接步骤箭头，不能因其图上孤立而误报为流程不可达。终止信息可以无出口。边的存在只证明图形连接，不证明条件有解；用户需要时另用规则模型验证平衡和可达性。

SVG或PNG需检查文字、回流箭头及裁切；只生成源码或通过XML解析时，明确未做视觉预览。不把一次模板样例运行当成所有游戏循环的行为验证。

## 随附渲染器的JSON格式

```json
{
  "title": "循环名称",
  "width": 1000,
  "height": 700,
  "start": "act",
  "loops": [
    {"id":"main", "label":"行动循环", "x":500, "y":350, "width":960, "height":660,
     "global_information":["coins"]}
  ],
  "nodes": [
    {"id":"coins", "label":"当前金币", "kind":"information", "loop":"main", "x":500, "y":140},
    {"id":"act", "label":"采取行动", "kind":"action", "loop":"main", "x":250, "y":340},
    {"id":"result", "label":"行动结果", "kind":"information", "loop":"main", "x":700, "y":340}
  ],
  "edges": [
    {"from":"act", "to":"result", "label":""},
    {"from":"result", "to":"act", "label":"再次行动", "via":[[700,540],[250,540]], "label_x":475, "label_y":520}
  ]
}
```

- 坐标单位为SVG逻辑像素，x／y是节点中心；默认节点180×72。画布、节点与via坐标必须有限且位于画布内，节点不能重叠。
- `kind`只支持`action`、`information`、`branch`、`subloop`四类，不再接受旧的`step`、`decision`、`terminal`。四类均用圆角框及约定颜色。节点ID为英文字母起始的字母、数字或下划线；图中文字可用中文。
- `loops`逐个提供循环体的ID、名称、边界坐标／尺寸及`global_information`信息节点ID列表。每个节点的`loop`必须对应已声明循环体，且坐标在该边界内；全局信息必须为本循环体的信息节点，不得作为步骤边端点。列表为空时提供`global_information_note`说明“无”或“待确认”。
- 全局信息区域由指定信息节点的边界计算，需在这些节点上方预留38像素标题、四周预留12像素，并避开循环体名称和流程节点。子循环节点可用`loop_ref`指向本图已展开的循环体；未在本图展开时，在交付物中保留子图引用与信息清单。
- 每条边可提供`via`折线转折点；`label_x/y`成对提供以避免文字遮挡节点。需换行的标签使用换行符。脚本不自动排版或防止线条交叉，生成后仍须检查。
- 输出目录必须独立于插件源码。已有同名产物时脚本拒绝覆盖；只有用户授权替换旧产物时才使用`--overwrite`。
- `loop-check.json`报告环、步骤可达性与无标签分支边，全局信息单列，不误报为不可达。没有环可能是在画局部流程，应修正图的名称或补充真实返回条件，不自动补造回流。
- JSON可以另外记录`rule_ref`、`loop_level`等设计属性；脚本只消费布局与连线字段，不执行任何玩法表达式。

工具调用例：

```text
python scripts/render_loop.py <graph.json> --output-dir <项目产物目录>
```

普通Mermaid路径无需Python：手写`flowchart`，使用同一套节点和边清单，并说明未生成图像。用户指定其他图形工具时以其格式为准；若有匹配工具技能，按该技能使用，不自行安装或连接外部账号。
