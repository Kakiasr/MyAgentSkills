# 游戏系统设计

## 职责与边界

把用户的零散需求、游戏规则或现有设计整理为可交接的“系统树＋配置表＋行为契约＋验收”。既能从零建树，也能只修改已有树中的相关部分。

正式文档集采用“一系统一文档”：每份系统文档只有一个`SYS-*`顶层系统根，路径为`systems/<SYS-ID>-<slug>.md`。跨系统总览只写职责、依赖、接口和链接；不得建立包住全部系统的游戏总树。公共ID、所有权和交接规则见[插件级路由与交接契约](../../references/skill-routing-and-handoff.md)。

分析现有游戏取得证据交给`game-analysis`；本技能接收其规则、证据状态与具体缺口，不把推断自动升级为已确认需求。用户要求边拆边建树时按需衔接，原作事实与复刻选择分别记录。

不以函数／场景目录替代需求，不把整理任务变成重新设计游戏。体验与玩法取舍交给`game-design`；玩家循环图交给`game-loop-design`；实现架构与代码交给`game-programming-development`。没有这些工具时仍可完成本技能范围内的文档，不声称完成其他专业工作。

## 文档粒度与系统树根节点

- 一份系统文档只描述一个系统；多系统需求先划分职责，再按系统分别输出文件，不把全部系统拼进一份总文档。
- 系统树必须以当前文档所描述的系统作为唯一顶层节点，例如“符号系统（SYS-SYMBOL）”。不在其上增加游戏名、“游戏系统”或“全部系统”等总根，也不把其他独立系统放成并列根。
- 当前系统内部的对象、行为和确属其职责的子系统可以展开；独立外部系统只写依赖、接口、事件／规则ID与文档链接，不复制其完整设计。
- 当前系统的配置、数据、状态、行为、需求与验收随该系统文档组织。确需拆附件时仍只服务该系统，主文档提供引用与唯一事实源位置。
- 总览只提供系统索引、边界与关系，不承载各系统详细规则。既有合并文档按系统拆分时保留图例和稳定ID，维护旧位置→新文档的引用映射。

## 按需读取

- 每次新建或实质修改，先读[系统树模板](templates/system-tree-template.md)。按风险裁剪，不机械填满全部章节。
- 修改已有树时，另读[增量转写规则](references/incremental-update.md)，再读用户文档及受影响的引用定义。
- 首次采用格式、需要完整填写示例或核对作用域时，读[五步开箱示例](examples/five-step-chests.md)。示例数值仅作演示，不是新项目默认值。
- 面临多来源结算、随机、生命周期、重复／恢复或证据与需求混淆时，读[系统树设计约定](references/system-tree-contracts.md)。

## 工作方式

1. 确认交付是新建、补充、替换、转写还是评审；找出原文件、图例、版本、ID习惯及正式规则来源。若用户要求修改既有树但未提供树，索取该文档；可先列候选补丁，不虚构原树。输入混有多个独立系统时，先划定系统职责与`SYS-*`，分别建文档；外部系统在当前树中只保留接口引用。
2. 将输入拆成独立需求，保留出处。区分用户已确认规则、建议／假设、冲突和未知。只追问会改变实现结果的缺口；其他缺口列具体待决策项，不自行填成确定规则。
3. 找出系统职责、对象所有权、静态配置、运行数据、状态与行为。复用已定义对象；需求对象不自动等于单个引擎类。一个可变字段只指定一个权威写入者。
4. 用树表达归属、状态与有序编排；重复内容放配置表，行为按独立触发和操作拆行。一个内容可有多个行为，多句原文也可共同约束一个行为，不机械“一句一条”。
5. 每条行为语义化填写触发条件、目标、效果、数值、次数限制、结算时点；另写失败、例外、覆盖顺序、反馈和恢复。明确AND／OR、资源成本与奖励、实例与共享份数、在场与持有范围、阶段与提交点。
6. 按功能风险补关系、随机、公式取整、生命周期、连锁、竞争和存档；无此机制注明不适用，不因模板有该栏就加入新机制。
7. 增量修改时维护追溯表和变更清单：新增、修改、复用、冲突、待决策；更新引用及受影响验收，不擅自重排或改号无关系统。
8. 验证字段语义、引用、所有权及正常／失败／重复／边界结果。分别报告文档校验、数值模型核算和实际游戏测试，不相互冒充。

## 交付

- 范围、状态与待决策项；系统树；实际需要的配置、数据和行为表；验收用例。
- 正式文档集默认每系统一份；系统索引由`game-design-document`维护。孤立小功能可只交单系统文件，不强制生成整个项目文档集。
- 有既有树时，优先交付可定位补丁和影响范围；用户要求完整新版时再合并输出，保留无关已确认内容。
- 原输入→对象／规则ID→验收的追溯；新增假设和冲突单列。
- 写文件时尊重用户目标位置；未指定可使用当前项目文档目录。不得改写插件本身作为普通系统设计的默认产物。

## 不可省略的质量边界

- 用户原始“图例”逐字保留；图例是允许节点的约定，不是要改写的示例树。用户已有格式优先；冲突需说明，不静默改图例。
- ID不使用行号、当前顺序或层级路径；已有名称／ID稳定，跨表引用不产生第二套事实源。
- 不把关键词摘句、复制完整段落到各字段当成语义化。未明确字段只能是明确共享规则引用、不适用原因或具体问题，不能解释成无条件／无限次／全目标。
- 配置、说明对照、实际行为与权限约束分开；动画、事件订阅和原说明不能各自重复发奖。
- 不将示例中的“5行动”“13金币”、固定游戏类型或单一结算顺序变成所有项目的要求。
- 原创规则是设计决定；逆向材料是证据。实际行为与文本冲突要登记采用哪条；正文不依赖恢复工程才能理解。
- 没有字段级缺口不代表已经实现；文档、模型、引擎与玩家验证分开标记。
