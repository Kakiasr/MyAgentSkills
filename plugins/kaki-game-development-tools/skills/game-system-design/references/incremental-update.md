# 零散需求转写与既有树增量更新

## 读什么

先读用户树的说明卡、图例、命名和ID约定。再读取变更涉及的对象、共享规则、表与验收；追踪其直接消费者。不需要为了修改一句规则无条件遍历整个项目。

原树不存在或只给出局部时，不宣称已经合并。可输出“待迁入补丁”，明确所缺定义；不能把未见到的无关系统重新编造一遍。

新增规则写入所属系统的独立文档，系统树以该系统为唯一顶层。跨系统变更分别列出各文档补丁，通过接口／事件／规则ID互相引用，不合并为游戏总树。旧文档混写多个系统时，拆分只迁移归属与引用，保留图例、稳定ID及确认规则；总览留下索引，不再保留另一套详细规则。

## 转写过程

1. 记录每段用户输入的原意和出处，拆出玩家行为、触发、目标、资源、时点、限制和例外。允许一段包含多条规则；原句不是行为的固定粒度。
2. 为每条需求选择新增、修改、复用、冲突或待决策。仅因术语不同不能新建第二个对象；先检查现有语义。
3. 复用名称、ID、归属和唯一写入者。没有ID的旧文档可用现有唯一名称定位，不为一次小修改全树重编号。
4. 将变更写到唯一事实源；树用引用保持可读，表中维护具体条件和数值。更新引用、状态、事件、数据有效期及受影响用例。
5. 对比修改前后：哪些结果改变，哪些保持；特别检查成本／奖励、重复输入、禁用、目标失效、存档与多来源效果。

## 冲突处理

新需求与已确认规则矛盾时，指出原值、新值和实现差异。用户已明确要求替换的同一范围可直接改，并登记变化；未明确的优先级、条件或范围列问题，不静默覆盖。

重要字段尚缺：在该行为标“待决策Q-ID”，问题表写明不同答案会导致的结果。不得仅写“按公共规则”却没有可查的规则ID或正文。

## 补丁格式

- 基线：文件／版本或用户提供的片段。
- 新增：具体插入位置、名称／ID、正文。
- 修改：旧规则定位、新规则、原因。
- 复用：被引用的对象／参数／共享规则，不重复定义。
- 删除：仅在用户明确要求替换或删除的范围执行，说明被引用方如何迁移。
- 待决策：具体字段、选项差异及受阻行为。
- 验证：新增或受影响用例及未执行事项。

要求完整新版时把补丁合并成一致文档，并附变更摘要。文本移动或表格拆分不等于新功能，不能凭此修改玩法或将草案标为已确认。
