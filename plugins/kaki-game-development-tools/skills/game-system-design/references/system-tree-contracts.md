# 系统树设计约定

以下保留首次逆向归纳的设计原则与风险清单；最终输出结构使用同技能的`templates/system-tree-template.md`（v2），不机械复制所有章节。历史案例用于说明歧义，不作为其他游戏的默认规则。

日期：2026-10-18。用途：让策划、程序、美术、测试对同一条需求作出一致解释。
性质：基于《幸运房东》发行包恢复脚本的设计推导，不是原游戏自带规范；实时玩法部分为迁移示例，尚未经实际项目验证。

## 1. 交付结构

一个功能的最小交付只有三部分：系统说明卡、需求树、验收用例。实现语言、引擎类名、源码位置放在独立映射附录，不混入设计规则。

- 系统说明卡：目的、范围、外部依赖、需求状态、负责人/版本。已有信息不重复填写。
- 需求树：对象、配置、数据、状态、行为、事件、资产。
- 验收：具体初始条件、一次操作、期望数据、期望反馈；可重现失败时附复现步骤。

复杂系统按需增加事件契约表、数值表、状态转移表、结算时序、实现映射。树中引用它们，不复制同一规则的多个版本。
原用户提供的“图例”保持原文，不在需求实例中重写。本规范解释节点用法，不替换原图例。元信息、规则说明、验收表位于树外；不为它们增加强制树节点。

## 2. 节点语义与归属

| 节点 | 必须回答 | 边界 |
| --- | --- | --- |
| 系统 | 负责哪一种需求，交付什么结果 | 一个系统不自动等于一个类、场景或管理器 |
| 类 | 哪一类可重复创建的对象共享哪些定义 | 只有复用有价值时使用，不强制画继承树 |
| 对象 | 谁持有数据，谁执行行为，何时创建/结束 | “面板”“玩家持有集合”“本轮结算器”均可为需求对象 |
| 配置/配置库 | 开始运行前定义、由设计人员调整的规则 | 配置的编辑位置只指定一次；实例不能写回共享配置 |
| 数据 | 运行中记录什么，由谁唯一写入 | 明确类型、初值、范围、生命周期、是否保存 |
| 状态/枚举 | 哪些情况互斥或可以并存，允许如何改变 | 同一枚举中的值互斥；独立状态域不得硬拼成一个枚举 |
| 行为 | 什么触发，什么条件，执行什么，结果是什么 | 行为下的直接步骤从上到下执行；并行必须明说 |
| 条件判断？ | 对什么作判断，命中后执行哪条路径 | 两个分支使用“是/否”；多分支必须互斥并有未命中结果 |
| 事件/通知/订阅 | 什么事实已经发生，谁何时响应 | 事件不替代需要立即得到成功/失败结果的操作调用 |
| 资产 | 需要什么图像、声音或表现资源 | 使用逻辑资产ID、尺寸/时长/状态要求，避免只写“播放特效” |

包含关系只表示职责/所有权；执行顺序仅在同一个“行为”的步骤中成立。不同对象的兄弟顺序不表示更新顺序。
共享对象只定义一次，其他位置使用引用。一个可变字段只指定一个写入者；其他系统通过行为请求修改。

## 3. 命名与引用

- 对象用名词：“符号候选面板”；行为用动宾：“提交符号选择”；事件用已发生事实：“符号已获得”。
- 一个概念只有一个正式名称。不得交替使用“删除”“移除”“摧毁”表达同一未定义概念。
- 小功能可只用唯一名称。发生跨树引用、跨成员交接或版本追踪时，再增加 SYS/OBJ/CFG/DAT/STA/ACT/EVT/AST 编号。
- ID不包含层级路径，不因节点移动改号。引用写作“引用 EVT-001 符号已获得”。
- [草案]/[已确认]/[已实现]/[已验收]为需求状态。[新增]/[修改]/[删除]为相对明确版本的变更状态，两者不混用。
- 逆向项目的[观察]/[推导]/[未知]保留在证据附录；正式开发需求只接受已经作出决定的规则。

## 4. 行为契约：六项必填，四项按风险添加

六项必填：触发入口、允许状态/前置条件、执行步骤、数据结果、玩家反馈、失败结果。允许填写“无玩家可见反馈”，但要说明可观察结果在哪里。
按风险添加：成本提交点；重复请求；中断恢复；并发/竞争顺序。只要涉及资源、存档、异步、连锁或多来源写入，就必须填写对应项。

行为规范写法：

- 提交符号选择（ACT-001）
  - 当前状态为
    - 等待选择
  - 选择会话有效且候选仍存在？
    - 是
      - 1. 将选择状态切换为已结束，锁定本次提交
      - 2. 请求持有集合创建所选类型的一个实例
      - 3. 成功？
        - 是
          - 关闭面板，显示获得反馈
          - 通知
            - 符号已获得（EVT-001）
        - 否
          - 恢复等待选择，保留原候选，显示失败原因
    - 否
      - 保留原数据，不扣资源，忽略失效请求

“1.”表示步骤号而不是额外节点类型。行为触发来自玩家输入或外部事实事件；同一事实不要既直接调用又订阅一次造成双执行。

## 5. 数据与配置字段

第一次定义字段时，至少给出：类型/单位、初值、合法范围、唯一写入者、有效期、存档策略。例如：

| 字段 | 定义 |
| --- | --- |
| 移除代币余额 | 非负整数/枚；初值由新局配置提供；资源账户唯一写入；整局有效；保存 |
| 本次移除费用 | 非负整数/枚；由基础费及当前修正规则计算；移除会话持有；提交前重算；不单独保存 |
| 待入账金币 | 有符号整数/枚；初值0；结算账户写入；本次结算有效；读档策略必须明确 |
| 当前候选列表 | 类型ID有序列表；面板会话写入；选择结束销毁；未完成选择时保存具体结果 |

避免“永久数值”这种没有边界的表述：明确指本局、账号、实例生命周期或跨变形保留。
配置缺失、引用不存在、存档版本不同的处理也属于需求；开发不得自行选择静默回退还是报错。

## 6. 数值、随机与关系规则

数值必须给公式、单位、正负边界、倍率叠加方式、舍入模式、舍入时点、修改优先级。公式必须附两个可计算例子；包含负数时必须有负例。
“四舍五入”必须说明0.5与负半值；不依赖引擎默认。数值范围可能溢出时指定上限/数值表示策略。

随机必须说明：候选池→过滤→权重/概率→抽取方式→重复策略→空池处理→保存/复现策略。
稀有度百分比不是类型权重；必须说明先抽稀有度还是将全部类型一起加权。
“随机选20个”不足以定义转轴算法；存在分列、聚团、保留位或空位补偿时必须明确。
种子重放是可选开发能力，不得因为代码调用随机数就推定原项目支持重放。

空间关系必须定义坐标、边界、对角、环绕、自身是否计入、重复目标、道具修正规则。关系查询结果不自动等于可生效目标，仍须检查效果条件。

## 7. 状态、请求与跨系统契约

每个状态至少说明：入口、允许请求、禁止请求的结果、退出条件、退出清理。单纯布尔值可以表达正交状态，不必强制转成大枚举。
两个请求可能竞争时，选一种处理方案并写明：固定优先级、按到达顺序串行、只接受首个、后者替换前者。不要强制所有项目采用同一种方案。

事件契约表至少包含：唯一名称、发布者、发布时间、最小载荷、订阅者、同步/排队方式、重复与失效处理。
例如“符号已获得”：在持有集合成功写入后发布；载荷包含实例标识、类型、获得原因；失败不发布。实例标识是开发约定，不推定原游戏已有稳定UUID。
“请求支付租金”不是“租金已支付”；需要立即返回是否成功时先调用行为，成功后才发布事实。

## 8. 连锁与效果结算扩展

仅当出现生成、变形、销毁、反应链或多个修改者时启用。必须补全：

1. 阶段及每阶段进入/退出条件。
2. 阶段内排序、同优先级顺序；不得凭树中对象排列推定。
3. 目标读取时点：入队快照还是执行时重新查询。
4. 变化提交时点：立即还是批次后；销毁与移除分别定义。
5. 触发次数范围：每事件、每目标、每轮、实例终生；定义去重键及何时清理。
6. 重算影响范围：自身、邻接、全场或持有集合。
7. 稳定/结束条件；数值改变、队列为空、动画完成不能混为一个判断。
8. 非终止保护：上限/环检测/调试中断；触发后哪些数据保留、哪些收益不得提交。

不要把原游戏的特殊分支全部抽象为通用引擎。只有预计存在多个内容使用者时才建立通用配置；单个特殊效果可以独立行为加明确接口。

## 9. 表现、异步与存档扩展

“数据完成”和“表现完成”分开定义。需求要说明动画期间是否锁输入、是否可跳过、跳过是否直接展示最终结果。
如果要求不同速度结果一致，要成为验收项；静态代码阅读不是证明。
资源入账必须区分：已确定收益、待显示收益、真实余额。支付检查使用哪一种余额要写明。
存档必须指明保存时机、未完成选择、未入账收益、异常关闭、版本迁移。事务写入、临时文件替换或入账去重令牌是实现建议，是否采用由项目风险决定。

## 10. 三档使用成本

| 档位 | 使用时机 | 必交 |
| --- | --- | --- |
| S：单人原型 | 一个功能，单一写入者，无跨帧交易 | 一段系统说明＋小树＋正常/失败验收各1例 |
| M：小团队交接 | 多对象/跨系统/可调数值 | S＋字段契约＋事件引用＋边界/重复/恢复用例 |
| L：复杂功能 | 连锁、联机、异步付费、跨版本存档 | M＋阶段/竞争顺序＋诊断记录＋专项回归矩阵 |

不按公司规模决定档位，按功能风险决定。小型独立游戏也可能有L档结算器，其设置菜单仍可用S档。

## 11. 评审门槛

交接前必须能回答：谁触发？谁写数据？配置从哪里来？允许在哪个状态执行？失败是否扣费？成功后通知谁？何时反馈？重复/中断怎么办？如何验收？
出现以下情况则退回修改：

- “适当增加”“正常结算”“随机出现”“永久保留”“播放对应特效”且无进一步定义。
- 两个对象都直接维护同一余额，或者同一公式在两处各写一遍。
- 只列函数、字段和文件，没有玩家操作与外部结果。
- 只写成功路径，失败、空池、失效目标没有结果。
- 编造的设计约定被标成逆向确认事实。

## 12. 从案例到规范的对应

| 《幸运房东》发现 | 规范要求 | 漏写后的开发分歧 |
| --- | --- | --- |
| 旋转先检查状态且消耗1金币 | 行为入口、成本、拒绝结果 | 有人实现免费旋转，有人只在动画按钮禁用 |
| 移除/重掷费用受细则修正 | 费用配置唯一来源与覆盖顺序 | UI显示1但后端扣2 |
| 候选先稀有度后类型抽取 | 分阶段概率、去重、空池 | 稀有符号概率随类型数量意外改变 |
| 转轴洗牌/分列/空位交换 | 显示容量不等于抽样算法 | 把20格误当成均匀无放回抽20 |
| 永久字段与历史形态并存 | 生命周期/继承字段/价值归属 | 变形后丢失加值或重复计算 |
| 效果分阶段重算且有动画等待 | 时序、去重、提交点、结束条件 | 同效果重复触发，动画速度改变结果 |
| 租金检查计入待入账与汇总收益 | 余额语义与交易时点 | 明明付得起却判定失败 |
| 存档保存复杂未完成状态 | 恢复策略须单列 | 读档重新抽卡或重复发钱 |

## 13. 迁移到实时游戏的纸面检查

例：冲刺。数据包含体力/点、速度/米每秒、持续时间/秒；状态为可冲刺/冲刺中/冷却；输入为按键请求；行为明确扣费、方向锁定、碰撞退出、冷却；资产为启动/持续/停止反馈。
验收必须包含重复按键、体力不足、受击打断、不同帧率。伤害与冲刺竞争时项目必须决定优先级。
这说明节点语言能容纳实时需求，不证明物理、网络预测或回滚规范已经验证；此类项目需增加更新频率、权威方和同步扩展。

## 14. 依据与边界

这些字段契约、分档和验收门槛来自本次逆向后的设计推导，不是原游戏内置格式，也不依赖另行安装外部知识库。
本规范经静态案例追踪与纸面交接检查，尚未经过另一位开发者独立实现及用户测试。下一次修订以实际“开发需要追问的问题”和实现偏差记录为依据。
