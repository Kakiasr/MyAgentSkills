# 游戏设计文档

## 目标

把用户提供的创意、资料和已确认规则整理为一套可供策划、程序、美术与测试共同使用的游戏设计文档集。用户要求复刻现有游戏时，以指定版本和范围为基线，区分原作事实、推断、复刻决定与原创改动；未知项不能用惯例补成确定规则。

本技能负责编排、统一口径、装配文档和做跨文档验收。各专业结论仍由对应技能产生：

- `game-analysis`：现有游戏的观察、规则、数值、内容与实现证据。
- `game-design`：目标体验、核心玩法、动作、决策、反馈与原型假设。
- `game-loop-design`：玩家循环、层级节律、失败／退出与可编辑循环图。
- `game-system-design`：系统树、配置、数据、行为契约、例外与验收。
- `game-programming-development`：把实现交接路由到软件架构、玩法实现、Unity工程工具及测试验证专项。
- 只有交付范围包含视觉、资产或渲染约束时，才按[美术专项交接契约](../../references/art-specialist-contract.md)调用对应的美术指导、内容设计、2D／3D生产、渲染、管线或图形性能专项。

不要用本技能替代某个专业技能，也不要为了填满文档调用与范围无关的技能。

本技能只负责正式文档集，不负责一般项目推进、代码实现或资产生产；这些任务由`game-development-workflow`协调。所有跨技能交接遵守[插件级路由与交接契约](../../references/skill-routing-and-handoff.md)。

## 每次先读

1. 读取[插件级路由与交接契约](../../references/skill-routing-and-handoff.md)和[文档集契约](references/document-set-contract.md)，确定权威所有权、文件、状态、ID、追溯和完成度规则。
2. 读取[文档集模板](templates/game-design-document-set.md)，按项目风险裁剪章节；不得删除用于揭示未知、冲突和验证状态的结构。
3. 再读取将要调用的专业技能 `SKILL.md`，并依其路由读取必要的 references、templates 或 examples。复刻任务通常先读 `game-analysis`；新创意通常先读 `game-design`。

## 编排流程

1. **建立任务基线**：记录游戏／项目、目标版本、平台、目标设备、输入方式、资料来源、复刻范围、明确排除项和交付位置。只有会改变文档结构或实现结果的缺口才追问；其余建立 `Q-*` 待决项。
2. **登记输入而不抢先解释**：为用户陈述、录像、截图、规则、源码和授权发行包建立来源ID。把内容分成已确认事实、观察、推断、用户决定、假设、冲突和未知。
3. **选择最小技能链**：
   - 复刻：`game-analysis` → `game-design`（体验解释／取舍需要时）→ `game-loop-design` + `game-system-design` → `game-programming-development`（要求可实现交接时）。
   - 原创：`game-design` → `game-loop-design` + `game-system-design` → `game-programming-development`（要求实现交接时）。
   - 已有明确规则：可直接从 `game-system-design` 开始，不强制重做体验设计或技术拆解。
4. **建立单一规则基线**：稳定ID贯穿体验、循环、系统、需求、配置和验收。相同数值或条件只在一个权威位置定义，其他文档引用；不得在多份文档中维护互相独立的副本。
5. **装配文档集**：默认生成项目索引、原作拆解、体验与玩法、循环、系统索引、每系统独立文档、跨系统需求、配置索引、集成验收与追溯。系统正文只写入`systems/<SYS-ID>-<slug>.md`；项目级文件不复制单系统规则。用户未提供原作或某文档不适用时，在索引说明原因，不伪造内容。
6. **做一致性审查**：逐项核对动作、目标、成本、奖励、随机、单位、取整、次数、状态、结算顺序、失败、重复、中断、存档、反馈和资产需求。循环节点引用实际规则ID；需求引用系统行为；配置字段有消费者；验收覆盖正常、失败和高风险边界。
7. **报告完成度**：分别给出资料提取、语义核查、配置覆盖、文档闭环、数值模型、引擎实现和实际游玩验证状态。只有声明范围内没有未解决阻塞项且验收可执行时，才称“可直接用于复刻”；否则明确为可实施草案或部分基线。
8. **执行自动校验**：创建或更新`document-set.json`，运行`node scripts/validate_document_set.mjs <文档集目录>`。修复错误；警告要修复或在交付摘要解释。未运行校验时不得称跨文档一致性已验证。

## 完整游戏拆解的默认交付

当用户指定一款完整游戏或发行包并要求“拆解一次／完整拆解／复刻／还原”，而没有限定为某个单一机制时，本技能是默认总入口，即使用户没有显式说“文档集”。必须执行复刻技能链并创建实际的多文件文档目录；`game-analysis`报告只是`01-original-game-analysis.md`的输入，不能成为最终替代品。

至少交付以下可区分产物：

- 游戏体验与玩法拆解：体验目标、玩家动作、决策、约束、反馈、失败、节律和构筑空间。
- 游戏循环：宏观、单局及关键子循环，包含入口、返回、退出、失败和规则ID引用。
- 系统文档：先建立覆盖矩阵，再对范围内每个独立系统实行“一系统一文档”。
- 需求与配置：单系统需求、配置、例外和验收归入所属系统文档，项目级文件维护跨系统接口及索引。
- `document-set.json`和自动校验结果。

资料不全时，照常创建上述结构并写入已确认内容；未知项使用`Q-*`和覆盖状态，不得因缺少运行验证而省略整类文档。若受上下文、工具或时间限制不能一次完成，明确报告“阶段成果”并继续完成剩余文件，不得把聊天中的综合摘要称为完整拆解。

## 输出要求

- 默认输出为一个目录中的多份 Markdown 文档；一份系统文档只写一个系统，按系统分别创建文件。当前系统的需求、配置和验收归入该系统文档，配置量较大时可附该系统专属CSV。
- 聊天回复只用于进度和交付摘要，不能替代默认的目录与文件。只有用户明确要求聊天概览、单文件或不落盘时才改变输出介质，并说明因此无法完成的校验层级。
- 多文件交付必须包含`document-set.json`机器清单，格式见[清单模板](templates/document-set.example.json)。单文件交付不强制清单，但必须明确无法执行完整跨文件校验。
- 系统树以当前系统为唯一顶层根，不加游戏总根，不在一个树中完整展开所有独立系统。外部系统仅写依赖、接口、事件／规则ID及文档引用；确属当前系统内部的对象和子系统可在根下展开。
- 总览文档仅作系统索引、边界和关系说明，不承载全部系统详细规则。用户要求单文件时，交付当前一个系统；请求同时涉及多个系统而又限定单文件时，明确范围冲突并请用户选定系统，不静默合并所有系统。
- 使用模板约定的文件名；已有项目有命名规范时服从项目规范，并在索引给出映射。
- Mermaid 循环图必须同时保留节点／边语义；只有实际渲染或预览后才声称视觉验收通过。
- 需求规格写“系统必须产生什么可观察结果”，程序架构写“如何实现”；不得用类名、函数名或场景树替代需求。
- 配置表必须包含字段ID、类型、单位、默认值或来源、合法范围、作用域、修改者／所有者、使用时点、引用规则和未知状态。未知值留空并引用 `Q-*`，不得填入看似合理的占位数值。
- 复刻只覆盖用户有权分析和实现的对象；不绕过 DRM、付费验证、加密访问控制或反作弊，不复制或分发无权使用的原作资源与源码。

## 收口门槛

- 每份系统文档只对应一个系统，树根与当前系统名称／ID一致，跨系统引用可解析且没有复制完整外部系统。
- 索引声明的每个文件存在，版本和基线一致。
- 每条关键结论能回溯至来源／证据或明确的用户决定。
- 原作事实、体验解释、实现建议和原创修改没有混写。
- 所有跨文档ID可解析；没有孤立配置、无消费者事件或无验收关键需求。
- 覆盖矩阵列出纳入、部分覆盖、未覆盖和不适用，不用“完整”掩盖未知范围。
- 交付摘要列出已确认、假设、冲突、待决策、阻塞项、未执行验证和下一步负责人。
