# 游戏设计文档集契约

## 默认文件集

| 文件 | 权威内容 | 主要来源技能 |
| --- | --- | --- |
| `00-index-and-decisions.md` | 基线、版本、范围、术语、决策、冲突、待决项、文档地图 | 本技能 |
| `01-original-game-analysis.md` | 原作事实、证据、覆盖矩阵、内容母表、未知项；原创项目可不适用 | `game-analysis` |
| `02-experience-and-gameplay.md` | 体验承诺、核心玩法、动作、决策、反馈、失败与验证假设 | `game-design` |
| `03-gameplay-loops.md` | 各层玩家循环、返回／退出条件、可编辑图 | `game-loop-design` |
| `04-system-index.md` | 系统文档索引、职责边界与跨系统关系；不写详细规则或游戏总树 | 本技能 |
| `systems/<系统ID>-<系统名>.md`（每系统一份） | 当前系统的说明卡、系统树、对象、配置、数据、状态、行为、需求、例外与单系统验收 | `game-system-design`；专业技能供稿 |
| `05-requirements.md` | 项目级约束与跨系统接口索引；单系统需求引用所属系统文档，不重复正文 | 本技能装配；专业技能供稿 |
| `06-configuration-tables.md` | 配置表目录与跨表引用索引；字段、值来源和校验正文在所属系统文档／专属附件 | `game-system-design` |
| `07-acceptance-and-traceability.md` | 跨系统集成验收与追溯索引；单系统验收引用所属文档 | 本技能 |

按范围裁剪文件，不适用项在索引登记。大量可机器编辑的数据另存 CSV；Markdown 保留字段字典、主键、外键、单位、范围和表间关系。

多文件文档集另含`document-set.json`，它是校验索引而非规则正文。清单登记文件、系统归属、实体ID、定义位置、引用、需求验收和配置消费者；格式见`templates/document-set.example.json`。每次交付前运行`node scripts/validate_document_set.mjs <文档集目录>`。

## 一系统一文档

系统文档按系统职责拆分，而不是把所有系统树、所有配置或所有行为分别堆入几份全局大文档。每份系统文档的树以当前系统名称／ID为唯一顶层；不能以游戏总根包住全部系统。外部独立系统仅写接口、依赖、事件／规则ID和链接，不复制其详细设计。内部对象或确属本系统职责的子系统可以在当前根下展开。

总览只维护索引、边界与关系。旧`04-system-design.md`若混写多个系统，迁移为`04-system-index.md`及各系统文件，保留图例、ID并登记链接映射；不要自动改写用户已有文档，只有本次交付或明确授权的迁移范围才执行拆分。

## 状态模型

- 来源：`观察`、`声明`、`实现证据`、`推断`、`用户决定`、`未知`、`冲突`。
- 需求：`草案`、`已确认`、`已实现`、`已验收`。
- 覆盖：`已覆盖`、`部分覆盖`、`未覆盖`、`不适用`。

不得因写入正式文档就把推断变成已确认，也不得因代码存在就把行为标成已验收。

## 稳定ID

推荐前缀：`SRC`来源、`E`证据、`DEC`决定、`Q`待决、`EXP`体验、`LOOP`循环、`SYS`系统、`OBJ`对象、`CFG`配置、`DAT`运行数据、`STA`状态、`ACT`行为、`EVT`事件、`REQ`需求、`NFR`非功能需求、`AST`资产、`AC`验收。

- ID不使用行号、标题层级或当前排序。
- 已分配ID不因移动、拆文档或改名而复用。
- 删除项保留墓碑和替代ID；合并项列出旧ID。
- 同一事实只在权威条目定义，其他位置使用ID引用。

## 需求写法

每条需求至少包含：ID、状态、来源规则、主体、触发／前置、必须产生的结果、失败结果、优先级、验收ID。涉及数值时引用配置字段；涉及反馈时说明可观察通道；涉及保存时说明恢复结果。

非功能需求只在有项目依据时加入，并给测量环境、指标和阈值。不要自动写“高性能”“低延迟”“支持扩展”。

## 配置表契约

每张表说明用途、主键、粒度、生命周期、版本和消费者。每个字段记录：字段ID、名称、类型、单位、是否必填、默认值或来源、合法范围／枚举、作用域、唯一修改者、读取／结算时点、引用规则、校验和未知项。

随机配置还要说明候选池、过滤、权重语义、抽取、重复、空池和种子策略；公式还要说明取整、边界、优先级和至少两个可计算例子。

## 一致性检查

1. 每个关键玩家动作均有系统行为、反馈和验收。
2. 每条循环边的条件能定位到规则或决定。
3. 每个 `REQ` 有来源和 `AC`；每个关键 `ACT` 至少被一条需求与验收覆盖。
4. 每个 `CFG` 字段有消费者；运行数据与配置不混用。
5. 成本、奖励、失败、重复和中断在体验、系统、需求及验收中结果一致。
6. 原作冲突已选择复刻基线或明确阻塞，未静默择一。
7. 所有“完整”“一致”“已验证”均附范围、版本和验证层级。
8. 自动校验无错误；警告已修复或在交付摘要说明理由。脚本通过只证明结构与引用一致，不等于规则正确、实现完成或玩家验证通过。
