# 游戏体验与玩法设计

## 职责

负责回答“玩家要感受到什么、通过什么操作和决策产生这种感受、系统给出什么反馈”。定义体验承诺、核心玩法、玩家能力、目标、约束、失败与原型假设。不负责维护完整系统树、绘制正式游戏循环图或决定程序架构。

显示名改为“游戏体验与玩法设计”；保留内部名称`game-design`及原资料路径，兼容已有调用。

## 专业边界

- 零散规则整理、系统树新建／转写／增量修改、配置与行为契约：交接`game-system-design`。
- 行动—反馈—奖励—再次进入的循环、层级节律与循环图：交接`game-loop-design`。
- 单纯整理已有规则时，不要求用户重新定义核心体验；只有玩法取舍实际不明确时才参与决策。
- 技术架构和代码交给`game-programming-development`；全局视觉语言交给`game-art-direction`，具体内容交给对应美术专项。系统树中的需求对象不等于引擎类。

## 依据

涉及核心体验的定义、选择、拆解、评审或验证时，先读取 `references/core-experience-design.md` 的来源约定及相关章节，并读取 `references/core-experience-design-errata.md` 中对应页的勘误。该参考是用户提供的《游戏核心体验设计》200 页校注转写，不再是摘要。需要完整评审时阅读全文；引用应标明 PDF 页码。

原文、编辑补录与项目假设必须区分。缺损标记不能当作已知内容；需要逐字核实时读取 `references/core-experience-design-source.md` 与对应原页图。原文公式、履历和案例评价未进行外部事实核验；发现疑误时不得静默修正或把它转为强制开发规则。

涉及体验目标、核心玩法或动作与反馈取舍时使用本技能。综合策划案按需要与系统、循环技能协作，不重复维护其产物。如果当前环境另有`gamedesign`技能，可按需结合其知识库；它不是执行本插件的前提。外部资料与本插件的体验术语不一致时说明差异，并以本参考作为本插件的体验分类标准。用户明确规则优先于默认假设，但要指出内部冲突。

不要把参考资料中的案例结论当成不可违背的定律。理论框架、经验公式和体验分类用于提出与检验设计假设，最终以目标玩家测试和项目证据为准。

## 工作模式

按问题选择最小深度，公共ID和交接遵守[插件级路由与交接契约](../../references/skill-routing-and-handoff.md)。需要正式结构时读[体验与玩法模板](templates/experience-gameplay-template.md)。

- **快速澄清**：一句话定义、目标玩家、核心动作—反馈和最关键假设；不强制完整体验谱系。
- **标准设计**：完成核心体验、玩法、动作反馈、最小内容集和原型验证，适用于大多数项目。
- **完整评审**：用户要求全面体验分析、分类映射或长周期审查时，才阅读全文并使用完整体验谱系与多时间尺度。

## 工作流

1. 提取目标玩家、平台、游戏时长、镜头、操作方式、玩家幻想与制作限制。
2. 使用 `references/core-experience-design.md` 定义核心体验：先确定目标玩家，再明确主导体验及体验之间的支持或冲突关系，不预设主辅体验的数量上限；写出体验承诺、支撑机制、节律、纵向层次、对比关系、破坏因素和终点感受。
3. 定义核心玩法：玩家动作、对象、目标、约束、反馈和失败。
4. 用最小玩法片段检验动作、决策、反馈和失败能否支撑体验；可简述重玩动机，不以此代替正式循环图。
5. 列出支撑玩法所需的系统候选与输入事实，交给`game-system-design`定义系统边界和需求契约。
6. 当任务涉及循环、成长节律或循环图时，将已明确的玩家动作与动机交给`game-loop-design`；缺失的成长或长周期不得凭空补造。
7. 把所有未被用户确认的补充标为 `假设`，并给出最小验证方式。
8. 将确定后的规则交接给程序、美术设计和技术美术技能。

## 交付物

- 一句话游戏定义与目标玩家。
- 核心体验声明：目标玩家在典型游玩时段内反复形成的主导感受，以及该感受如何从操作层发展到自我叙事层。
- 标准／完整模式说明主辅体验关系；仅完整评审要求系统性24类体验谱系映射及不选其他体验的理由。
- 体验支撑矩阵：机制、节律、纵向层次、对比关系、破坏因素、终点感受和验证方式。
- 核心玩法：动作、对象、目标、约束、决策、反馈与失败；相关系统和循环的交接输入。
- 玩家动作与系统反馈表。
- 与体验取舍直接相关的资源、奖励、失败及难度假设；正式数值、状态、系统树由系统设计技能维护。
- 内容最小集与推迟项。
- 原型需要验证的设计假设。
- 面向程序、美术和技术美术的交接约束。

## 质量门槛

- 每个系统必须服务于明确体验或玩法目标。
- 核心体验不能只写抽象情绪词，必须能追溯到玩家行为、系统机制、反馈节律与时间尺度。
- 说明体验之间如何增强或争夺注意力；数量取决于项目，不将编辑偏好冒充原稿限制。
- 以第 197 页六个问题检查体验。10 秒、10 分钟、10 小时与操作、认知、情感、自我叙事是分析视角，按实际游戏时长和目标选用；不要求所有项目覆盖全部尺度。章节层次图中损坏的 L4 层名不得自行恢复。
- 必须指出体验的对比基线、张力与释放方式，以及至少一个会破坏体验的断点。
- 每个玩家动作必须有可感知反馈。
- 若简述循环，说明再次进入的动机；需要正式图或循环评审时使用循环设计技能。
- 数值规则必须写明单位、边界、取整和结算时机。
- 随机规则必须说明候选池、过滤、权重和保底或可复现策略。
- 不用“有趣”“爽”“丰富”等词代替可实现规则。

- 现有游戏的事实采集、内容清点、实现追踪与规则还原：交接`game-analysis`；体验解释可协同，但不能把设计意图或玩家感受推断写成实测事实。
