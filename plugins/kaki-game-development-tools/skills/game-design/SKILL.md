# Game Design

## 职责

负责回答“玩家为什么玩、反复做什么、依据什么决策、系统如何反馈、怎样形成可持续体验”。不替程序决定代码结构，不替美术决定最终视觉语言。

## 依据

涉及核心体验的定义、选择、拆解、评审或验证时，先读取 `references/core-experience-design.md` 的来源约定及相关章节，并读取 `references/core-experience-design-errata.md` 中对应页的勘误。该参考是用户提供的《游戏核心体验设计》200 页校注转写，不再是摘要。需要完整评审时阅读全文；引用应标明 PDF 页码。

原文、编辑补录与项目假设必须区分。缺损标记不能当作已知内容；需要逐字核实时读取 `references/core-experience-design-source.md` 与对应原页图。原文公式、履历和案例评价未进行外部事实核验；发现疑误时不得静默修正或把它转为强制开发规则。

涉及核心玩法、核心系统、核心循环、交互链、系统图或正式策划案时，使用本技能的工作流与交付标准。如果当前环境另有 `gamedesign` 技能，可按需读取其知识库和模板；它不是安装或执行本插件的前提。外部资料与本插件对“核心体验”的术语或分类不一致时，说明差异，并以 `references/core-experience-design.md` 作为本插件的输出标准。用户明确给出的项目规则优先于默认假设，但要指出内部冲突。

不要把参考资料中的案例结论当成不可违背的定律。理论框架、经验公式和体验分类用于提出与检验设计假设，最终以目标玩家测试和项目证据为准。

## 工作流

1. 提取目标玩家、平台、游戏时长、镜头、操作方式、玩家幻想与制作限制。
2. 使用 `references/core-experience-design.md` 定义核心体验：先确定目标玩家，再明确主导体验及体验之间的支持或冲突关系，不预设主辅体验的数量上限；写出体验承诺、支撑机制、节律、纵向层次、对比关系、破坏因素和终点感受。
3. 定义核心玩法：玩家动作、对象、目标、约束、反馈和失败。
4. 定义核心循环：进入条件、行动、结算、奖励、成长和再次进入。
5. 划分核心系统与周边系统，明确系统边界和相互依赖。
6. 补充关卡、内容、经济、进度、难度、教程和可访问性规则中与本次目标相关的部分。
7. 把所有未被用户确认的补充标为 `假设`，并给出最小验证方式。
8. 将确定后的规则交接给程序、美术设计和技术美术技能。

## 交付物

- 一句话游戏定义与目标玩家。
- 核心体验声明：目标玩家在典型游玩时段内反复形成的主导感受，以及该感受如何从操作层发展到自我叙事层。
- 主体验与辅体验的关系、24 类体验谱系映射及不选其他体验的理由。
- 体验支撑矩阵：机制、节律、纵向层次、对比关系、破坏因素、终点感受和验证方式。
- 核心玩法、核心系统、核心循环。
- 玩家动作与系统反馈表。
- 资源、奖励、失败、成长和难度规则。
- 内容最小集与推迟项。
- 原型需要验证的设计假设。
- 面向程序、美术和技术美术的交接约束。

## 质量门槛

- 每个系统必须服务于明确体验或玩法目标。
- 核心体验不能只写抽象情绪词，必须能追溯到玩家行为、系统机制、反馈节律与时间尺度。
- 说明体验之间如何增强或争夺注意力；数量取决于项目，不将编辑偏好冒充原稿限制。
- 以第 197 页六个问题检查体验。10 秒、10 分钟、10 小时与操作、认知、情感、自我叙事是分析视角，按实际游戏时长和目标选用；不要求所有项目覆盖全部尺度。章节层次图中损坏的 L4 层名不得自行恢复。
- 必须指出体验的对比基线、张力与释放方式，以及至少一个会破坏体验的断点。
- 每个玩家动作必须有可感知反馈。
- 每个循环必须说明玩家为何再次进入。
- 数值规则必须写明单位、边界、取整和结算时机。
- 随机规则必须说明候选池、过滤、权重和保底或可复现策略。
- 不用“有趣”“爽”“丰富”等词代替可实现规则。
