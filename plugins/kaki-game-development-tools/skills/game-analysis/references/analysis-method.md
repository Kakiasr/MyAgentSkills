# 拆解方法与证据约定

## 选择范围，而不是套全量报告

| 用户问题 | 优先路线 | 交付与停止点 |
| --- | --- | --- |
| 为什么想继续玩／体验如何形成 | 代表性游玩片段、动作反馈、选择后果、张力释放 | 机制到体验的解释与待测假设；不假装已读源码 |
| 这个符号／装备如何结算 | 文本、配置、效果实现、调用入口与提交顺序 | 行为字段、共享阶段、例外及边界用例 |
| 内容有多少／是否有配置表 | 构建对应内容注册表、加载器、过滤与可获得条件 | 母表总量、解析量、语义核查量、可获得范围；表名不是配置存在的充分证据 |
| 完整系统或面向重建 | 在用户授权范围内分系统建立覆盖矩阵 | 可独立理解的规则、未决项、验收与交接；未知不填成建议 |
| 两个版本有何变化 | 分别固定身份、按稳定内容ID匹配、兼容证据比较 | 已确认差异、推断、不可比较范围；序号／混淆名不是稳定ID |

## 证据索引

每条证据记录：证据ID、游戏版本／平台、来源类型、文件／页码／时间戳／函数或地址、内容范围、观察结果、限制。发行包记录原始文件SHA-256、包内逻辑路径及派生产物身份；多个文件不把一个EXE的摘要当成整套游戏身份。文件行号需绑定文件版本；地址需绑定模块与构建。报告优先引用用户可打开的相对文件和精确位置。

证据类型与断言层分开：

- 玩家可见观察：某次操作或录像内确实出现什么；附初始条件、操作序列、结果、重复次数。
- 静态材料：说明、配置、源码或反编译；指出是声明值、可达调用链还是伪代码推断。
- 模型核算：明确输入规则、假设、穷举／采样范围，验证的是模型而非原游戏执行。
- 推断：列支持、反例和可证伪实验；“开发者为了……”通常属于推断。
- 未知：具体缺哪个分支、版本、条件或证据，下一步怎样查；不以百分比置信度替代依据。

规则状态可用“仅声明／静态追踪／运行观察／交叉支持／冲突／未知”，同时保留来源类型和边界；没有一个全局等级能覆盖所有字段。一次运行可支持效果发生，却不能证明概率值准确。源码确认概率公式，仍需核查调用时的候选过滤和随机输入。

## 从实现到设计语言

沿“玩家／系统入口→前置条件→目标选择→效果与资源变化→结算提交→后续事件→反馈”闭合。给重要字段指定权威写入者；本次文档只描述原作证据支持的所有权，不自行重构架构。

行为字段至少包括：规则ID、内容ID、触发条件、目标、效果、数值与单位／公式、次数与作用域、结算阶段、失败／例外、证据与核查状态。复杂随机补候选池、先过滤还是先抽取、权重、放回、重抽／保底、随机状态；复杂数值补加乘覆盖顺序、封顶、取整、临时与永久增益。未知数值不得用显示文本反推成确定公式。

“移除”“销毁”“消耗”“转化”“离场”分别确认，不能合并；事件名只作实现定位，正文写谁在何条件下改变哪些状态。动画和通知不是重复发奖来源。描述规则时保留前提、范围、次数和时点，避免把局部逻辑写成全局规则。

## 覆盖与冲突

以内容注册表／规则入口清单作母表。记录总条目、已提取、已语义拆解、已边界核查、已运行观察及未知；各列可重叠，不能相加当总数。按实际范围逐条核查，不能以同一脚本遍历所有名称宣称逐条完成。

冲突表列来源、版本、条件与差异；先查版本／平台／模式／调用覆盖。无法消解则并列报告。用户决定复刻以哪种行为为基线后，才形成开发需求，保留原作事实与复刻选择的区别。

## 专业交接

- 给体验与玩法设计：观察片段、动作反馈、选择成本、体验解释及反例；不要把解释当玩家研究结果。
- 给系统设计：稳定规则／内容ID、字段化行为、共享结算阶段、配置／数据／状态、冲突与具体缺口、验收案例和证据索引。系统树正文可独立实现，证据在旁核查；未知阻止“完整复刻”承诺。
- 给循环设计：入口、动作、成本、反馈、结果、返回条件、失败退出、局内／跨局变化及对应规则ID。未观察到跨局成长就不补成长。
- 给程序开发：已确认的需求基线和验证向量，不把反编译的类名强制变成新项目架构，不复制未获授权的原作资源或代码作为默认方案。
