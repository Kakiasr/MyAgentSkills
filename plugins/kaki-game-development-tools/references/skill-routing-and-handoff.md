# 插件级路由与交接契约

## 两个总入口

- `game-development-workflow`负责**推进工作**：识别阶段，选择专业技能，安排制作、集成、调试与验收。用户要规划、实现、修复或推进项目时使用它。
- `game-design-document`负责**形成正式文档集**：装配、更新、迁移、审查和校验可追溯文档。用户要策划案、复刻文档、需求集、配置表或正式交接包时使用它。
- workflow在阶段成果需要成为正式基线时交给document；document发现规则、证据或实现缺口时回交对应专业技能。二者不得维护第二套专业结论。
- 单专业请求直接进入专业技能；不要为了经过总入口而增加无关交付物。

## 权威所有权

| 内容 | 权威技能／位置 | 其他位置如何使用 |
| --- | --- | --- |
| 原作事实、证据与覆盖 | `game-analysis` | 引用 `E-*`，不得改写证据等级 |
| 体验承诺与玩法取舍 | `game-design` | 引用 `EXP-*` |
| 玩家循环与循环图 | `game-loop-design` | 引用 `LOOP-*`及关联行为ID |
| 单系统规则、行为、配置、数据与验收 | `systems/<SYS-ID>-<slug>.md` | 项目级文件只索引或引用 |
| 跨系统需求与接口 | `game-design-document`的项目级需求文档 | 单系统文件引用相关 `REQ-*` |
| 程序实现映射 | `game-programming-development` | 引用设计ID，不反向改写设计 |
| 视觉方向 | `game-art-design` | 资产与技术美术引用 `VIS-*` |
| 资产生产记录 | `game-art-asset-creation` | 引用 `AST-*`和视觉／行为ID |
| 渲染与性能约束 | `game-technical-art` | 使用 `TA-*`／`NFR-*`并附测量条件 |

## 状态与稳定ID

来源状态：`观察`、`声明`、`实现证据`、`推断`、`用户决定`、`未知`、`冲突`。需求状态：`草案`、`已确认`、`已实现`、`已验收`。验证层级：`文档`、`模型`、`引擎`、`玩家`。这些维度不得互相替代。

推荐ID：`SRC`、`E`、`DEC`、`Q`、`EXP`、`LOOP`、`SYS`、`OBJ`、`CFG`、`DAT`、`STA`、`ACT`、`EVT`、`REQ`、`NFR`、`VIS`、`AST`、`TA`、`AC`。ID不使用行号或层级路径；移动或改名不换ID；删除保留墓碑；同一事实只在一个权威位置定义。

## 最小交接包

每次跨技能交接至少包含：目标、版本、范围与排除项；输入ID、来源状态和权威位置；确认结论、假设、冲突、未知与受阻项；新增或修改ID及下游影响；接收技能要回答的问题和期望产物；已做与未做的验证。

接收技能必须复用已有ID；需要改变上游结论时创建 `DEC-*` 或 `Q-*` 并回交，不静默覆盖。

## 一系统一文档

- `04-system-index.md`只保存系统目录、职责边界、依赖与跨系统关系，不包含游戏总树或单系统规则正文。
- 每个系统使用独立的`systems/<SYS-ID>-<slug>.md`，且只有一个`SYS-*`顶层根。内部对象可展开；外部系统仅以ID、接口和链接引用。
- 单系统行为、字段、配置、例外及验收正文只在该系统文档定义。项目级需求、配置和验收文件仅维护跨系统内容与索引。
- 系统拆分、合并或迁移必须保留旧ID映射、引用更新和受影响验收，不因文件重排改变规则。

## 变更传播

| 上游变化 | 至少复核 |
| --- | --- |
| `E/DEC/EXP` | 循环、系统规则、需求和验收 |
| `ACT/CFG/STA/EVT` | 循环边、跨系统接口、实现映射、资产反馈和验收 |
| `LOOP` | 体验节律、行为引用、反馈频率和性能预算 |
| `VIS/AST` | 资产生产、导入、渲染预算和可读性验收 |
| `REQ/NFR` | 系统文档、实现、技术美术及集成验收 |

变更完成后记录修改ID、直接消费者、已更新文件和仍待复核项。
