# 内容设计

## 项目入口与交付

在 minigame 项目根执行；先读根/目标目录最近 AGENTS、`Assets/Skills/README.md`，再按任务读取 `Assets/Game/Documentation/INDEX.md`、相关术语和功能文档。对象内容以 `Assets/Game/Configs/配置总表.xlsx` 为编辑源；历史备份、旧报告与旧字段不参与新内容生成。

共同状态和回退见 `Assets/Game/Documentation/Project/内容生产工作流.md`。已有资产覆盖与所有场景写入沿用 `Assets/Skills/project-work-order/SKILL.md`；候选在 Assets 外，清单由助手填写，用户无需维护 JSON。按需使用 `Tools/Content/README.md` 的清单及只读校验器。不能用“新建文件再改引用”绕过覆盖队列。

候选、正式落盘、Editor 验证和实际运行分别报告；只执行当前任务授权的检查。消费者文件存在与 hash 一致不证明运行接线。发送其他聊天前遵循已有通信授权，不由技能新增发送权限。

## 设计与实现顺序

中文名称为“内容设计”，稳定调用ID为`minigame-design-config`。覆盖卡牌、贴纸、标签的玩法内容；图像制作交静态美术或对应专项。用户只要方案时交方案，不写游戏配置和代码。

1. 以稳定对象ID对齐配置总表、功能规则和当前实现。区分用户已确认目标与代码现状；名称、行号、资源旧花色文件名不能代替身份。用户只填写现有可见列，助手处理隐藏ID、内部参数和注册。
2. 将效果分析为触发事件、条件、作用对象、执行顺序、数值运算、持续范围与重入规则；分析供实现使用，不再要求用户编辑原子库。端口与定位只作设计评估。同款判定、等级与占槽、数值语义读取当前术语及功能文档，不在技能中另存常数表。
3. 已确认内容先写回总表候选，再实施领域行为和内部配置映射。卡牌、贴纸、标签按各自实际列处理，不给三者强加同一种数据结构。提供数值与效果框分开，空基础文案不能从旧字段补句；永久成长只更新绑定数值。
4. 按职责实现调用链，并核对失败不消耗资源、重复事件不重复结算、双面和多槽实例身份、跨房/存档状态。公共契约由指定集成人收束。缺失的能力应实现或明确交接，不能仅更新`ConfigMasterReview.json`冒充实现。
5. 仅做必要内联，还原后与总表原文逐字相同。效果的原子句式沿用已确认标准；“获得”和“额外提供”的永久性与独立结算按当前语义分别实现。真实歧义只询问受影响内容，其余工作继续。

## 变更审阅与候选失效

修改玩法源码后先运行`python3 Tools/Content/CheckGameplayContract.py`。命中变化时审查恢复边界、更新检查点纪元，再由集成人使用`--record --reason "实际审阅依据"`记录。不得只刷新指纹，也不将拒绝旧存档说成已完成旧存档数据迁移。检查范围和保守策略以工具当前说明为准。

## 配方与交付

修改配方先审查前置可达性、材料身份、同卡/同面条件、解锁是否消耗及槽位容纳；不得默认为消耗合成。只调整任务范围内内容，效果强度或路线存在实质歧义时给具体选择。

执行 `python3 Tools/Content/PrepareConfigMaster.py --output output/Implementation/<任务>`，成功后运行 `ValidateContentHandoff.py <输出>/Handoff.json`。PreparationState必须为ready且绑定当前Handoff；失败或中断留下的旧候选不可覆盖。工具自动检查源码、表、审阅依据与目标新鲜度；失败说明具体原因，不从旧输出取文件覆盖。运行消费者、配方来源或表发生变化，重新审阅后生成。

给集成人：总表增量、实现路径、效果与数值绑定、候选清单、实际检查结果和用户验证入口。落盘后复读总表及配置，用 `--phase applied` 校验；未验证的触发情形明确列出。不要用旧配置兜底掩盖缺失定义。
